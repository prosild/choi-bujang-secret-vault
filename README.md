## 11단계 작업 저장점 기록

XDR 6종도 같은 저장소에 구현했습니다. 제공된 가상 경보 158건에서 block/alert/record는 각각 53/52/53이며 정상 이벤트 차단은 로컬 검토상 0건입니다. 운영 엔진에 검증된 주체·기기·목적지 연결을 넣는 어댑터가 있으며, 연결이 없으면 차단을 집행했다고 표시하지 않습니다. 각 xdr 폴더의 README에 재현 방법과 한계가 있습니다.

## 10단계 저장점 기록

1) 안전 정책은 `src/decider.mjs`, `aleph.config.json`의 `allowedRoutes`, `docs/db-policy-snapshot.json`의 DB 접근 정책입니다. DB 정책 사본은 2026-11-06 실제 메타데이터를 재조회해 RLS, 본인 소유자 정책 4개, 익명·일반 역할의 직접 조회 차단과 일치함을 확인했습니다. 운영 정책 파일이나 DB 정책은 수정하지 않습니다.

2) **정책 시험 사본 복원(2~3항)과 B 메모 복원(4~5항)은 별도 절차입니다.** 정책 복원은 artifacts 안의 시험 정책 사본만 대상으로 합니다. **B 메모 복원은 지정한 대상 한 건만 변경하며, 다른 메모와 다른 서비스 규칙은 건드리지 않고 기존 감사 기록을 보존합니다.** B 복원에서 정책 복원 절차를 실행하거나 감사 기록을 삭제·덮어쓰지 않으며, 복원 성공 기록만 추가합니다. 정책 시험의 계획 확인과 실행도 분리했습니다. `node scripts/policy-recovery.mjs prepare`는 현재 정책의 사본·SHA-256 해시·Git 버전과 `review.json`을 `artifacts/policy-<번호>`에 만들고, 별도 `test-copy/decider.mjs`의 기기 등록 규칙 한 줄만 바꿉니다. 사본 밖 `trust.json`에 manifest와 확인 계획의 해시를 따로 기록합니다. 출력된 폴더로 `node scripts/policy-recovery.mjs inspect artifacts/policy-<번호>`를 실행하면 **복원할 버전, 변경 파일·줄, 변경 전후 해시와 차이만** 확인할 수 있습니다. 이 명령은 복원하지 않습니다.

3) 변경 범위를 확인한 뒤 `node scripts/policy-recovery.mjs restore artifacts/policy-<번호>`를 실행합니다. **복원 직전에 사본과 manifest를 다시 읽어** 신뢰 해시, 확인한 버전, 바뀔 항목을 재검증하고 실행 전에 다시 표시합니다. 사본 누락·해시 불일치·버전 불일치·계획 후 변경은 쓰기 전에 중단합니다. 실제 경로가 프로젝트의 artifacts 하위인지 검사하며, 운영 정책이나 링크로 연결한 외부 파일에는 쓰지 않습니다. 복원 뒤 사본과 재대조하고 다른 서비스 파일·감사 이력을 보존합니다. `demo`는 같은 시험 사본 절차를 자동 실행하는 연습 명령입니다.

4) 자료 서비스는 `notes`, 복원 경로는 **`POST /api/restore`**, 본문은 `{ "id": "대상 UUID" }`입니다. 서명된 심판 시험 계정 B의 실행 ID·소유자만 허용합니다. B가 `/api/notes`로 처음 만든 한 건을 같은 트랜잭션에서 비공개 `vault_private.note_snapshots`에 revision 1로 보관하고 이후 변경으로 덮어쓰지 않습니다. SQL 시험 대상으로 정한 가상 B 메모 ID는 **`b6000000-0000-4000-8000-000000000010`**입니다. 이 고정 ID는 별도 재현용이며, 심판 실행에서는 해당 실행의 B 생성 응답 ID를 사용합니다.

5) 복원 요청 때 비공개 사본을 다시 읽고 ID·소유자와 내용 해시를 검증합니다. 사본이 없거나 해시가 다르거나 현재 대상의 소유자가 다르면 중단합니다. 검증된 사본의 값으로 대상 한 건만 복원한 뒤 DB에서 다시 읽어 **ID·소유자·내용 해시가 사본과 모두 같은지 대조**합니다. 불일치는 예외를 발생시켜 해당 트랜잭션을 롤백합니다. 다른 메모는 변경하지 않고 기존 감사 기록은 보존하며 성공 기록만 추가합니다. API도 반환된 ID·revision·해시 형식이 잘못되면 성공 응답을 거부하며 메모 본문·소유자·토큰을 반환하지 않습니다.

6) 실DB 재현 스크립트는 `scripts/verify-restore-db.sql`입니다. 기존 대상 ID가 있으면 중단하고 새 가상 B 한 건에만 변조 복구·삭제 복구·잘못된 사본 및 소유자 거부를 시험합니다. 다른 메모와 기존 감사 기록을 대조하고 시험 변경을 서브트랜잭션에서 롤백합니다. 앞선 실행 확인 만료 후 사용자의 재시도로 2026-11-06 **실제 Supabase SQL 시험 PASS**를 확인했습니다. 변조·삭제 복구, ID·소유자·내용 해시 일치, 잘못된 해시·소유자·대상 거부, 다른 메모·기존 감사 기록 보존을 검증했습니다. 시험 중 감사 2건이 추가됐고 시험 변경과 함께 롤백됐습니다. 별도 재조회 결과 기존 메모 5건, 사본·감사 0건, 시험 대상 없음입니다. 결과는 `verification/step10-db.json`에 기록했으며 실제 B 로그인·서명된 HTTP 왕복 시험과는 구분합니다.

7) 복구 후 1~9단계 재시험은 **`npm run test:recovery`** 한 줄로 실행합니다. 시험 정책 복원 → `node --test test/*.test.mjs` → `npm run decider:test` → `npm run fixture:7` → `npm run detect:test` → `npm run build -- --local` 순서입니다. 복원된 판정기의 정상 허용·미등록/금지 경로 거부, 모의 API에서 A 정상 CRUD·B의 A 자료 GET/PUT/DELETE 거부, 위조 서명·소유자·경로 거부를 검사합니다. 로컬·모의 검사 **38/38 PASS**, 판정기 4/4, 재인증 가상 시나리오, 탐지 6/6, 로컬 빌드 PASS입니다. 실제 서명된 B의 복원 HTTP 왕복과 운영 엔진 재공격은 별도 미실행입니다.

8) 「10단계 저장점」으로 커밋한 뒤 `npm run bundle`을 실행합니다. `artifacts/submission.json`에는 커밋·변경 파일·규칙·실제로 실행한 자체 점검만 담습니다. `bundle-notes.json`과 산출물은 Git에 넣지 않습니다. 기존 결과 화면의 통과 인정과 이번 코드의 검사 결과는 구분하며 제출은 사용자가 직접 합니다.

## 8단계 저장점 기록

1) 메모 `notes:<id>`는 개별 GET/PUT/DELETE, 공지 `announcements:<id>`는 개별 GET만 엔진 판정기에서 허용합니다. 전체 목록·강사 자료·알 수 없는 서비스·쿼리 기능 선택·export 경로는 거부합니다. 엔진의 `/notes/:id`와 앱의 `/api/notes/:id` 경로를 정확하게 대조합니다. 가명 subjectId를 DB 소유자와 비교하지 않습니다.
2) 기존 화면의 목록·메모 추가는 로그인한 본인 소유자 필터를 계속 사용합니다. 이 두 API는 엔진 allowedRoutes에서 제외합니다. 개별 조회·수정·삭제에도 서버가 검증한 실제 소유자 ID를 적용합니다. 공지는 `/api/announcements/:id`로 분리하고 서버가 공개 상태를 확인합니다. 공지 쓰기는 모든 일반 접속에서 거부하며 관리 경로는 아직 제공하지 않습니다.
3) `route_not_allowed`는 경로 거부 사유입니다. 운영 등록부의 허용 사유 코드 목록이 시작 틀에 없어 엔진 등록 여부는 미확인입니다. 공지 DB 생성·실제 조회 및 심판 평가는 아직 미검증입니다. 로컬 `node --test test/*.test.mjs`로 경로 위조·소유자 위조·공지 쓰기 거부를 검사합니다.

5) 아래는 과거 단계별 기록입니다. 특히 2단계의 공개 API 설명은 당시 상태이며 현재 인증된 API의 설명이 아닙니다.

## 5단계 저장점 당시 기록 (이력)

화면의 로그인·로그아웃과 메모 조회·추가·수정·삭제는 서버 함수로 요청합니다. 서버는 Supabase Auth와 안전한 쿠키로 로그인 세션을 관리하고 로그인 토큰과 메모 소유자를 확인합니다. Supabase의 `study_notes`에서 `PUBLIC`, `anon`, `authenticated`의 직접 테이블·열 권한을 회수했습니다. 적용한 권한 회수 SQL은 `scripts/step5-revoke-notes.sql`에 기록되어 있습니다.

사용자가 권한 회수 후 A의 메모 CRUD와 공개 키를 통한 원본 직접 요청에서 메모가 반환되지 않는 것을 확인했습니다. `anon` 및 `authenticated`의 테이블·열 유효 권한도 모두 false로 확인했습니다. 서버 로그인 변경 후 A·B의 로그인, 메모 CRUD, 새로고침과 로그아웃이 정상이라고 사용자가 확인했습니다. 화면 코드에는 Supabase 공개 키가 없으며, `aleph.config.json`의 원본 자료 주소는 쿼리가 없는 HTTPS 경로입니다.

로컬 빌드는 `npm run build -- --local`입니다. 최신 저장점의 Production 배포·비로그인 JSON 응답과 보안 헤더 및 심판 판정은 별도 확인이 필요합니다. 과거 공개 커밋과 배포에 남은 자료의 노출이 해소되었다는 증거는 없습니다.

## 최신 파일의 가상 메모 문장 검색 절차

현재 GitHub `main` 및 **현재 Production 배포**만 확인합니다. 검사 결과가 정상이어도 **옛 공개 커밋 또는 옛 Vercel 배포가 남아 있는 한 과거 노출이 해소됐다고 기록하지 않습니다.** 메모 문장은 학습용 가상 자료이며, 검색 결과 보고에는 메모 본문을 복사하지 않습니다.

### 1. GitHub 최신 커밋과 파일 확인

저장소를 로컬에 내려받은 뒤 다음 명령을 실행합니다. `origin/main`을 명시하여 작업 폴더의 미커밋 변경과 구별합니다.

```bash
git fetch origin main
git rev-parse origin/main
git ls-tree -r --name-only origin/main | grep -E '(^|/)data\.json$' || true
git grep -n -F -e '실습용 가상 과제 기록' -e '실습용 가상 포트폴리오 기록' -e '실습용 가상 리추얼 기록' -e '실습용 가상 행정 기록' origin/main -- . ':!README.md' || true
```

기대 결과는 `data.json`, `public/data.json` 경로가 없으며 네 문장에 대한 일치 결과도 **0건**인 것입니다. 이 README에는 검색 패턴 자체가 포함되므로 `README.md`는 검색에서 제외합니다. 다른 파일에 같은 문장이 나오면 해당 파일의 위치를 기록하고 공개 여부를 재검토합니다. `git grep`의 일치 결과가 전혀 없다는 사실과 실제 검사를 실행했다는 사실을 구분하여 기록합니다.
