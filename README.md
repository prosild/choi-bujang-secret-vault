# BYTE BACK 방어전 R5 — 2단계

현재 단계: 자료를 코드 밖으로 옮깁니다. 학습용 가상 메모는 Supabase `public.study_notes`에 보관합니다.

- `/`: 화면이 `/api/notes`를 호출하여 가상 메모 4건을 카드로 표시합니다.
- `/api/notes`: Vercel 서버 함수가 `SUPABASE_URL`과 서버 전용 `SUPABASE_SECRET_KEY`를 환경변수에서 읽습니다. 서버에서 Supabase를 조회하며 제목·본문만 반환합니다.
- `/data.json`: 생성하지 않습니다. 빌드도 오래된 `public/data.json`을 제거합니다. 새 배포에서 404 또는 메모 없는 응답을 확인합니다.
- `/aleph.json`: Vercel의 저장소·커밋·배포 URL을 빌드할 때 생성합니다. `aleph.config.json`은 `step: 2`입니다.

**현재 약점:** `/api/notes`는 아직 로그인이나 권한 검사가 없는 **공개 주소**입니다. 서버 전용 키는 브라우저에 노출되지 않지만 이 API를 비로그인으로 호출하면 네 메모의 제목·본문을 읽을 수 있습니다. 이것은 다음 단계에서 해결할 문제이며 보호 완료로 보고하면 안 됩니다.

## 실행 및 확인

1. Supabase SQL Editor에서 학습용 메모 4건과 RLS를 확인합니다. `anon` 및 `authenticated`에는 SELECT 권한을 부여하지 않습니다.
2. Vercel 프로젝트의 Settings → Environment Variables에서 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 **서버 환경변수**로 직접 설정합니다. 값을 Git, 브라우저 코드, 로그, 답변에 입력하지 않습니다. 설정 후 Production으로 재배포합니다.
3. 화면에 네 카드가 나타나고 `/data.json`이 메모를 반환하지 않는지 확인합니다. `/aleph.json`에서 실제 저장소와 커밋을 대조합니다. `/api/notes`는 공개라는 사실을 유지하고, 심판 확인을 대신하지 않습니다.
4. 로컬 정적 빌드: `npm run build -- --local`. 실제 Vercel 함수 동작은 이 명령으로 검증되지 않습니다.

실제 학생 자료와 비밀키는 코드·Git·제출물에 넣지 않습니다. `AGENTS.md` 규칙을 따르며 다른 단계의 예제는 보존합니다. 과거 커밋이나 과거 배포에는 가상 메모가 남아 있을 수 있습니다.

## 최신 파일의 가상 메모 문장 검색 절차

현재 GitHub `main` 및 **현재 Production 배포**만 확인합니다. 검사 결과가 정상이어도 **옛 공개 커밋 또는 옛 Vercel 배포가 남아 있는 한 과거 노출이 해소됐다고 기록하지 않습니다.** 메모 문장은 학습용 가상 자료이며, 검색 결과 보고에는 메모 본문을 복사하지 않습니다.

### 1. GitHub 최신 커밋과 파일 확인

저장소를 로컬에 내려받은 뒤 다음 명령을 실행합니다. `origin/main`을 명시하여 작업 폴더의 미커밋 변경과 구별합니다.

```bash
git fetch origin main
git rev-parse origin/main
git ls-tree -r --name-only origin/main | grep -E '(^|/)data\.json$' || true
git grep -n -F -e '실습용 가상 과제 기록' -e '실습용 가상 포트폴리오 기록' -e '실습용 가상 리추얼 기록' -e '실습용 가상 행정 기록' origin/main -- . ':!README.md' || true
```

기대 결과는 `data.json`, `public/data.json` 경로가 없으며 네 문장에 대한 일치 결과도 **0건**인 것입니다. 이 README에는 검색 패턴 자체가 포함되므로 `README.md`는 검색에서 제외합니다. 다른 파일에 같은 문장이 나오면 해당 파일의 위치를 기록하고 공개 여부를 재검토합니다. `git grep`의 일치 결과가 전혀 없다는 사실과 실제 검사를 실행했다는 사실을 구분하여 기록합니다.

### 2. 현재 배포의 비로그인 정적 응답 확인

현재 Vercel Production 배포 URL에서 로그아웃하거나 시크릿 창을 사용하여 다음 경로를 열어 봅니다.

| 요청 경로 | 정상 기대 결과 | 검사 항목 |
| --- | --- | --- |
| `/` | 200, 카드 4건(서버 API 로드 후) | 초기 HTML 응답에 가상 메모 본문이 직접 포함되지 않음 |
| `/data.json` | 404 등 또는 메모 본문이 없는 응답 | 예전 가상 메모 문장 0건 |
| `/aleph.json` | 200, 배포 식별 JSON | `repoUrl`과 `commit`이 GitHub 최신 커밋과 일치하고 메모 본문은 없음 |
| `/api/notes` | 현재 200, 가상 메모 4건 | **비로그인 읽기가 가능하다는 약점을 별도로 기록** |

브라우저 개발자 도구의 Network 탭에서 각각의 **응답 본문**을 확인합니다. 페이지 화면의 네 카드는 `/api/notes` 호출 후 표시되는 것이므로, 렌더링된 화면과 `/`의 최초 HTML 응답을 혼동하지 않습니다. `/aleph.json`의 `commit`을 앞서 확인한 `git rev-parse origin/main` 값과 비교하되, 새 커밋과 배포 시점 차이가 있다면 실제 배포 커밋을 따로 기록합니다. 비밀키나 메모 본문은 기록하지 않습니다.

### 4. 현재 남은 보호 한계

- `public/data.json`이 제거되고 Supabase의 `anon`·`authenticated` 테이블 읽기 권한이 없어도, **Vercel의 `/api/notes`는 서버 전용 키로 조회한 제목·본문을 비로그인 요청에 응답**합니다. 정적 파일 제거와 실제 접근 제어는 다른 문제입니다.
- 과거 공개 Git 커밋 및 기존 Vercel 배포에 남은 가상 자료는 최신 파일을 삭제했다고 사라지는 것이 아닙니다. **옛 공개 커밋과 옛 배포가 남아 있는 한 과거 노출은 해소되지 않았습니다.**
- 현재 단계의 자체 확인은 운영 심판 판정을 대체하지 않습니다.
